11The branching model

GitHub Flow has one long-lived branch and a rule about how changes reach it. Its simplicity is the point: the protection comes from the review gate, not from branch topology, so adding branches adds process without adding safety.

11.1The three principles#

11.2Why not GitFlow#

GitFlow maintains main, develop, release and hotfix branches simultaneously. It was designed for software shipped in versioned releases to customers who cannot upgrade on demand. Analytics platforms are rarely in that position: content is promoted to a small number of environments the team controls, and the cadence is iterative.

Applied to Fabric, GitFlow's additional branches mostly create additional workspaces to keep in step. Each long-lived branch wants a workspace connected to it, each workspace consumes capacity, and each pair is another thing that can drift. The review gate — which is what actually prevents bad changes reaching production — is identical in both models.

Note

Where a long-lived branch does earn its place

A release/<version> branch is worth introducing if you genuinely need to maintain a prior version while developing the next — for example a regulatory reporting solution where a filed period must remain reproducible. That is a specific, justified exception, not a default.

Practice

Review the branch list monthly

Branches whose date marker has passed and which have not merged are either abandoned or blocked. Both are worth knowing about. A branch list nobody prunes stops being useful within a quarter.

11.4Creating a branch#

A branch can be created in GitHub or from within Fabric. Creating it from within Fabric — through Branch out — is preferred because it creates the branch and the workspace together and connects them, which is the state you actually want. Section 12 covers that path.

To create a branch in GitHub directly:

  1. Open the repository and select the branch dropdown to review the existing branches. Check whether the work already has a branch before creating another.
  2. Select the branch count or the Branches link to open the branches page.
  3. Choose New branch.
  4. Enter the name following the convention above, and set the source to main.
  5. Create the branch. It is now selectable from the dropdown.
Rule

Always branch from current main

Branching from another feature branch couples two units of work: the second cannot merge until the first does, and reverting the first becomes complicated. If you genuinely depend on unmerged work, say so in the pull request and get the dependency merged first.

11.5Commit discipline#

Within a branch, commit frequently and keep each commit to a single logical change. The benefit is not tidiness for its own sake:

  • A reviewer can follow the reasoning commit by commit rather than confronting one large diff.
  • A single bad change can be reverted without unpicking unrelated work.
  • git log becomes a usable history of why the code is as it is, rather than a list of updates.

Note

A Fabric commit is a batch operation

Fabric commits the items you select in one commit. Atomicity therefore comes from selecting a coherent set of items rather than from committing one file at a time. The preview file-level commit capability narrows this gap for supported item types.
