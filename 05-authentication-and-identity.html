5Authentication and identity

The most common security mistake in this pattern is to use one identity for everything — typically a long-lived token belonging to whoever set the integration up. The platform pushes you away from that, because the interactive connection and the automation path use different identity types and cannot be collapsed into one.

Figure 2 sets out the two tiers and what each is used for.

5.1Why the split is unavoidable#

Fabric documents service principal authentication for the Git connection when the provider is Azure DevOps. For GitHub, the only documented credential for the workspace-to-repository connection is a personal access token, and the platform treats that synchronization as a user-delegated action authenticated by an individual's credentials. Plan on the basis that a non-human identity cannot own a GitHub Git connection, and re-verify before designing around any contrary behaviour you encounter — this is an area the platform has been changing.

The consequence is a deliberate two-tier model:

  • Tier 1 — interactive. Developers connect their branch workspaces and perform commits and updates using their own Microsoft Entra ID account and their own fine-grained personal access token.
  • Tier 2 — automated. GitHub Actions and any administrative automation authenticate as an Entra ID service principal whose credentials are held in environment-scoped GitHub secrets, and which is granted access to the target workspaces explicitly.

This separation is desirable independently of the platform constraint. A developer's token reaches only the repositories and branches that developer may touch. Automation credentials reach only the environment whose job is running. When someone leaves, revoking their account does not break the pipeline. When a pipeline is compromised, no individual's access is implicated.

Note

Authentication strength must match

The authentication method in Fabric must be at least as strong as the method required by the Git provider. If GitHub requires multi-factor authentication, Fabric must require it too. Mismatched strength causes connection failures that are not obviously about authentication.

5.2Tier 1: creating a fine-grained personal access token#

GitHub offers classic and fine-grained personal access tokens. Fine-grained tokens are the recommended choice because they can be scoped to a single repository and a minimal permission set, which a classic token cannot. Each person creates their own.

  1. In GitHub, open the account menu and go to Settings.
  2. In the left-hand navigation, choose Developer settings.
  3. Choose Personal access tokens → Fine-grained tokens, then Generate new token.
  4. Give the token a name that identifies its purpose, for example fabric-<proj>-sync, and set an expiry. Choose the shortest interval the team can operate with; treat anything beyond 90 days as requiring a stated justification.
  5. Under Resource owner, select the organization that owns the repository. Depending on organization policy, the token may require approval by an organization owner before it becomes usable.
  6. Under Repository access, choose Only select repositories and select the single repository for this project. Do not grant access to all repositories.
  7. Under Permissions → Repository permissions, set Contents to Read and write. This is the minimum required for Fabric to read from and write to the repository. Metadata: Read is granted implicitly and is required.
  8. Generate the token and copy the value immediately — it is not shown again. Store it in the organization's approved secret store, not in a file, a chat message or a note.
Caution

A personal access token is a credential, not a configuration value

Do not store tokens in the repository, in a shared document, in a workspace item or in a ticket. Do not share one token between people — doing so destroys the attribution that makes the audit trail useful, and means a single revocation blocks the whole team. Each person's token is their own.

Note

Classic tokens work, but are a poorer choice

A classic token with the repo scope will function. It also grants access to every repository the user can reach, which is exactly what least privilege is meant to prevent. Use fine-grained tokens unless an organization policy prevents it.

5.3Per-user connections in shared workspaces#

Connecting to a workspace that is already connected to Git prompts you to sign in to a Git account. This is expected: the Git connection is per user. Each person who works in the workspace configures their own connection from the Account details tab of the source control pane. With Azure DevOps the connection is often configured automatically; with GitHub each user supplies their own token.

Rule

Never pool a token across a team

The platform's own guidance is to configure individual connections rather than share a personal access token. Pooling a token means every commit is attributed to the token's owner, revocation affects everyone, and the audit trail cannot answer the only question it exists to answer.

5.4Tier 2: creating and configuring a service principal#

A service principal is a non-human identity in Microsoft Entra ID representing an application or service. Using one for automation decouples the deployment process from any individual's account and allows narrow, specific permissions to be granted.

  1. In the Microsoft Entra ID portal, register a new application. Record the Application (client) ID and the Directory (tenant) ID.
  2. Under Certificates & secrets, create a client secret. Copy the value immediately — it is not retrievable afterwards. A certificate is preferable to a secret where the organization's tooling supports it.
  3. Under API permissions, grant the permissions the automation actually requires for the Fabric service. Grant nothing speculatively; permissions are easier to add later than to explain in an audit.
  4. Have a Fabric administrator enable Service principals can call Fabric public APIs in the Admin portal under Tenant settings → Developer settings, and add this service principal — or, preferably, a security group containing it — to the allowed security group. If the automation must also create workspaces, connections or deployment pipelines through the API, enable Service principals can create workspaces, connections, and deployment pipelines as well.
  5. Add the service principal as a member of each target workspace, with the Admin or Member role, for every workspace the automation will act on.
  6. Store the tenant ID, client ID and client secret as environment secrets in GitHub, following Section 17.
Practice

Use a security group, not the principal itself

Adding a security group to the tenant allow-list and to workspace roles, and placing the service principal in that group, means the next service principal is onboarded by a group membership change rather than by a tenant setting change and a visit to every workspace.

5.5Credential lifecycle#

Localize

Record the rotation policy

Fill in the actual intervals, the owner of each rotation, and where the credentials are stored. A playbook that says 'rotate regularly' has not established a control.
