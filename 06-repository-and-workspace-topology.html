6Repository and workspace topology

Naming and structure decisions are cheap to make and expensive to change, because the workspace name, the Git folder name and the branch name are all part of the connection. Settle them before the first workspace is connected.

Figure 3 shows the three-way relationship between a workspace, the Git folder it is connected to, and the branch that folder sits on.

6.1The mirrored structure#

When a workspace is connected and synchronized, its structure — including subfolders — is reproduced inside the connected Git folder. Items in workspace folders are exported to folders of the same name; items in Git folders are imported to folders of the same name. Each item occupies its own folder containing a .platform file and the definition files for that item type.

Behaviour worth knowing before designing a structure:

  • Empty folders are not copied to Git. A folder appears in Git when an item is created in it or moved into it.
  • Empty folders in Git are deleted automatically.
  • Empty folders in the workspace are not deleted automatically, even after every item has been moved out.
  • Folder structure is preserved to ten levels of depth.
  • An item whose display name exceeds 256 characters, ends with a period or space, or contains a forbidden character has its Git folder renamed to the item's logical ID and type — which makes the repository considerably harder to read.

6.3Repository granularity: the decision to make deliberately#

The recommendation here is one repository per project, with one folder per layer workspace. Three alternatives are defensible, and the choice depends on how independently the domains in your estate release.
