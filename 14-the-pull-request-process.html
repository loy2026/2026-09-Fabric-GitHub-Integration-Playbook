14The pull request process

The pull request is where the quality of this whole model is actually determined. Everything else — branching, rulesets, environments — exists to make sure changes arrive here and cannot go around it.

14.1What a pull request is for#

Three things at once, and it is worth being explicit about all three because teams tend to optimize for the first and neglect the others:

  • A quality gate. A second person looks at the change before it reaches a deployable trunk.
  • A collaboration forum. Reviewers comment on specific lines, ask questions, and suggest improvements. This is the mechanism by which knowledge moves around a team and by which newer engineers learn the codebase.
  • A durable record. Six months later, the pull request is the answer to “why is this measure calculated this way?” — provided the description said something.

14.2Opening a pull request#

  1. Confirm the work is complete and committed to the feature branch, and that unit testing in the branch workspace has passed.
  2. In the repository, open the Pull requests tab.
  3. Select New pull request, or use Compare & pull request on the banner that appears after a recent push.
  4. Set the base branch to main and the compare branch to your feature branch.
  5. Review the Comparing changes section: check the commits, the files changed, and the additions and deletions. Read your own diff before asking anyone else to.
  6. Enter a title that describes the change, not the branch.
  7. Write the description — see the template below.
  8. Select Create pull request.

14.3What the description should contain#

A reviewer arriving at a Fabric pull request is looking at JSON they cannot execute. What they need from the author is context they cannot get from the diff.

14.4Reviewing#

Guidance for reviewers, in rough order of value:

  • Read the description first. If it does not say what the change is for or how it was tested, ask for that before reviewing the code. This is not pedantry — a reviewer who cannot tell what the change is intended to do cannot tell whether it does it.
  • Check the parameterization. Search the diff for hard-coded workspace names, lakehouse references, connection strings and database names. This is the single most productive thing a reviewer can look for in a Fabric change (Section 13.3).
  • Check the blast radius claim. Does the change touch a semantic model that reports depend on? Does a pipeline schedule change? Is a column removed that something downstream reads?
  • Ignore known noise. Column reordering in a .bim after a rename, and LF/CRLF conversion, are artefacts. Do not raise them.
  • Comment on lines, not in a summary. Line comments create a thread that can be resolved; a summary comment listing six issues cannot be tracked.
  • Approve, or request changes, explicitly. A review left in an ambiguous state blocks the author without telling them what to do.

To approve: open the pull request, select Files changed or the review control, choose Approve, add comments if useful, and Submit review. A reviewer must hold write access or above for the approval to count.

Note

What the author will see while a review is required

With the ruleset from Section 16 in place, the pull request shows Review required and Merging is blocked until an approving review from a user with write access has been submitted. This is expected and is the control working.

14.5Merging#

  1. Confirm the required approvals are present and every required status check has passed.
  2. Review the commit message and extended description that will be recorded on main.
  3. Select Merge pull request, then Confirm merge.
  4. Delete the feature branch when prompted. The branch has served its purpose and leaving it makes the branch list less useful.
  5. Update the Development workspace from Git — Section 14.6.
Practice

Enforce one strategy

A ruleset can require a specific merge method. Choosing one — squash, in most cases — and enforcing it keeps main's history uniform, which makes git log and git revert both behave predictably.

14.6Returning the change to the Development workspace#

A merge to main does not change any workspace. The Development workspaces connected to main must be updated before the change can be promoted.

  1. Open the Development workspace for the affected layer.
  2. Select Source control. The pending update count reflects the merge.
  3. Open Updates and review what will change.
  4. Select Update all, and confirm.
  5. Verify the update succeeded and that item status has returned to Synced.
  6. Repeat for each layer workspace affected by the change.
  7. Hand over to the release path: promote to Test and then Production with the deployment pipeline.
Rule

Update every affected layer before promoting

A change spanning bronze and silver requires both workspaces to be updated. Promoting one layer without the other produces a partially deployed change, which is harder to diagnose than an obviously failed one.

14.7Housekeeping#

  • Delete merged feature branches. Either manually at merge, or by enabling automatic branch deletion on the repository.
  • Delete branch workspaces when the release they support has shipped. They consume capacity and drift from main.
  • Delete preflight clones once the integration is stable and a baseline commit plus a successful round trip exist.
  • Prune stale branches monthly. A branch whose date marker has passed and which has not merged is either abandoned or blocked; find out which.
