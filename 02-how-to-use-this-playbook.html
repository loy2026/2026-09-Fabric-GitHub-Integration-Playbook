2How to use this playbook

2.1Reading paths#

The document is written to be read end to end once, then used as a reference. If time is short, these are the shortest useful paths through it.

2.2Conventions#

Note

On preview features

A number of capabilities described here — including several item types, branch workspace admin profiles, selective branching and file-level commit — were in preview at the time of writing. Preview behaviour changes without notice and is generally not covered by production support commitments. Verify the current state of anything you intend to depend on, and prefer a design that degrades gracefully if a preview capability is withdrawn.

2.3How to adapt rather than copy#

The temptation with a playbook is to adopt it verbatim. Three decisions genuinely depend on your context and should be made deliberately rather than inherited:

  • Repository granularity. One repository per project is the default recommended here. A single repository for an entire estate simplifies governance but couples release cadences; one repository per workspace fragments review. Section 6.3 sets out the trade-off.
  • Who may create workspaces. Branch-out is far more useful when developers can create their own workspaces. Many organizations restrict workspace creation to a central administration team. Section 12.4 describes the capability that reconciles the two.
  • How much automation to build. Sections 16 and 18 mark automated status checks as optional. The manual gates — required reviews, protected branches, environment approvals — deliver most of the risk reduction. Automated testing of notebooks and data quality is a worthwhile second phase, not a prerequisite.
