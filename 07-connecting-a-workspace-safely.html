7Connecting a workspace safely

This is the section to read before touching source-control settings. Connecting a workspace to a repository is a single dialog with a destructive failure mode, and the destruction is silent, immediate and not reversible. Everything that follows is a procedure designed around that one fact.

Caution

What actually happens when you connect

When a workspace is connected to a branch and folder, Fabric immediately makes the two match. If you then run Update workspace from Git while that folder is empty or near-empty, Fabric resolves the workspace to match — and removes items. A Git branch can always be restored to an earlier commit. A workspace cannot.

Figure 4 sets out the decision and both of its outcomes. The procedure in Section 7.3 exists to guarantee you take the left-hand path.

7.1Why the failure mode exists#

The rule Fabric applies to the first synchronization is reasonable in isolation: if one side is empty and the other has content, copy from the non-empty side to the empty one. If both sides have content, ask the user which direction to take.

The problem is what counts as content. A repository prepared in advance — with a README.md, a .gitignore, or placeholder layer folders created helpfully by whoever set it up — is not empty. The first sync therefore presents a choice, and one of the two options is Update workspace with Git content, which overwrites the workspace with a folder containing almost nothing. The dialog does warn, and asks for confirmation. It is nonetheless chosen, under time pressure, by people who reasonably assume that a fresh repository is empty.

Rule

Do not pre-create folders in the repository

Fabric creates the folder structure during synchronization. An 'empty' folder in GitHub containing only a README.md or a .gitkeep will not behave as empty. Create the repository, leave it alone, and let the first commit from the workspace populate it.

7.2Preflight: clone the workspace as a rollback target#

Because a workspace cannot be restored to a previous state, the only meaningful safety net is a second workspace holding a verified copy. A deployment pipeline stage is the most convenient way to produce one.

  1. Create or identify a spare target workspace to act as the clone.
  2. Use a deployment pipeline to deploy from the source workspace to that target. Fabric copies item definitions into the target.
  3. Re-hydrate the data. This step is not optional and is the one most often skipped — see the caution below.
  4. Run the clone. Execute the pipelines, refresh the models, open the reports. An unverified backup is not a backup.
  5. Record what the clone is for and when it may be deleted, so it is not mistaken for a live environment.
Caution

A pipeline clone does not copy data

For a lakehouse, Fabric creates a new, empty lakehouse in the target: no files, no tables. The SQL analytics endpoint and semantic model objects are provisioned, and notebooks and Spark job definitions are re-bound to the new lakehouse item. Shortcut definitions are synchronized; shortcut contents are not. Warehouse objects are created from the schema project, without row data.

A clone is therefore a functional shell until you load data into it. Treat re-hydration and verification as part of the preflight, not as a follow-up task.

7.3The connection procedure#

Perform these steps once per workspace. The workspace administrator performing them should have the repository open in a second window to confirm the folder state before proceeding.

  1. Confirm the preflight clone exists, has data, and runs.
  2. In GitHub, confirm the target branch exists and that the folder name you intend to use does not exist yet. You will type the folder name during connection; Fabric creates it.
  3. In the Fabric workspace, open Workspace settings.
  4. Select the Git integration tab.
  5. Choose GitHub as the provider. Sign in and authorize the connection when prompted, supplying the fine-grained personal access token created in Section 5.2.
  6. Enter the connection details: the GitHub organization, the repository, the branch (main for a layer's Development workspace), and the folder name (the layer code, for example BRZ).
  7. Read the summary in the dialog before confirming. It states which direction the first sync will take. If it offers a choice of direction, stop — the folder is not empty. Cancel, resolve the folder state, and start again.
  8. Select Connect and sync. With an empty folder and a populated workspace, Fabric copies workspace → Git and deletes nothing.
  9. Immediately open Source control, select all items under Changes, add a commit message such as baseline: initial workspace export, and Commit.
  10. Verify in GitHub that the folder now contains the expected structure and that the commit is present on the branch.
  11. Repeat for each layer workspace, using the same branch and a different folder.
Rule

Commit the baseline before doing anything else

Until a baseline commit exists on the branch, the workspace has no recoverable copy in Git and the whole exercise has added risk without adding protection. The baseline commit is the point at which the integration starts being useful.

7.4The folder synchronization pitfall#

This is a second, subtler version of the same failure, and it occurs long after the initial connection.

Because folder structure is part of what Fabric compares, creating a folder in the workspace that does not exist in the connected branch puts the two sides out of step. The source control pane reports uncommitted changes. If, at that point, someone runs Update from Git instead of committing, the branch's structure — which lacks the new folders — overwrites the workspace's structure, deleting the new folders and their contents.

Caution

Structural changes must be committed before any update

After creating or reorganizing folders in a workspace, commit that change before pulling anything. Do not run Update from Git with an uncommitted structural change outstanding.

Where the connected branch is protected and cannot be committed to directly — which, if Section 16 has been implemented, it will be — use the Checkout new branch option:

  1. In the source control pane, choose Checkout new branch. This creates a branch from the last synced commit and repoints the workspace's connection at it, without changing workspace content — so the uncommitted folder change is retained and ready to commit.
  2. Commit the folder changes to that new branch.
  3. Open a pull request and merge the change into the original branch through the normal review process.
  4. Switch the workspace back to the original branch, or update it, once the merge has landed.

7.5Recovery, if a workspace has already been emptied#

If the destructive path has already been taken, the options are limited and depend entirely on what exists outside the workspace.

Note

Recycle bin and Git integration interact badly

Git operations such as Undo or Update from Git re-create a deleted item with a new item ID, whereas restoring from the recycle bin preserves the original ID. Doing both produces two items with different identities, which can stop Git integration working and break existing dependencies. The mitigation is to delete the item that Git re-created. Note also that Git restores definitions only — a recycle bin restore returns both the definition and the data.
