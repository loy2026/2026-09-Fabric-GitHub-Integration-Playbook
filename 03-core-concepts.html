3Core concepts

Three platform mechanisms, one repository model and one branching model account for everything else in this playbook. Understanding what each is responsible for — and, more usefully, what each is not responsible for — prevents most design mistakes.

3.1Continuous integration and continuous delivery, in a Fabric context#

Continuous integration is the practice of merging changes from multiple contributors into a shared branch frequently, with automated verification on each merge. In Fabric terms it means that a notebook, semantic model or pipeline definition is committed to a branch, reviewed by someone other than its author, and integrated into a trunk that is known to be good.

Continuous delivery extends this so that an integrated change can be promoted to a test and then a production environment through a repeatable, auditable process rather than by hand. In Fabric terms it means that the content in main is deployed to the Development workspace, then promoted to Test and Production by a deployment pipeline that rebinds environment-specific configuration on the way.

The practical effect is a change of posture. Deployment stops being an event performed by the person who happens to know how the workspace is wired, and becomes a process that anyone on the team can run, that produces the same result each time, and that leaves a record.

3.2Mechanism one: Git integration#

Git integration is configured per workspace. Connecting a workspace to a repository branch and folder causes Fabric to serialize the definitions of supported items into that folder as text — JSON for reports and pipelines, .py for notebooks, a model.bim for semantic models, SQL project files for warehouses — and to keep the two in step through explicit Commit and Update actions.

What it is responsible for:

  • Version history of item definitions, with the ability to return to any earlier commit.
  • Isolated development through branches, and a branch workspace per branch.
  • Code review through the pull request mechanism of the Git provider.
  • The mirrored folder structure between workspace and repository.

What it is explicitly not responsible for:

  • Data. Lakehouse files and tables, warehouse row data and shortcut contents are not version-controlled. A lakehouse is represented in Git by a placeholder that records its existence and name.
  • Workspace configuration. Workspace access roles, capacity assignment and deployment pipeline definitions are managed in the Fabric service and are not part of the repository.
  • Unsupported items. Anything the integration does not support is ignored — not synchronized, but not deleted either. It appears in the source control pane and cannot be committed or updated.

3.3Mechanism two: deployment pipelines#

A deployment pipeline is Fabric's native release-management tool. It provides a small number of ordered stages — conventionally Development, Test and Production — and promotes content from one to the next. Its value is threefold: it gives release managers a controlled path that does not require Git expertise; it produces an auditable record of what was promoted and when; and, through deployment rules, it rebinds environment-specific configuration so that content behaves correctly in each stage.

Note

Deployment pipelines are documented separately

This playbook stops at the point where main is merged and the Development workspace is updated from Git. Stage configuration, deployment rules and promotion approvals are the subject of a companion release-management document. They are referenced here only where a decision in this playbook constrains them.

3.4Mechanism three: the Variable Library#

A Variable Library is a workspace item containing named variables, each with a set of values — one value set per lifecycle stage, or per developer. Exactly one value set is active in a workspace at a time. Consuming items resolve their values from whichever set is active, so the same definition behaves differently in different workspaces without being edited.

It can hold simple types and, more usefully, item references — a pointer to a specific lakehouse, for example. Items that can consume it include data pipelines, notebooks (through NotebookUtils and the %%configure magic), Dataflow Gen2, Copy Job, lakehouse shortcuts, user data functions and Plan items. It is itself a Git-supported, deployable item, so the configuration is versioned alongside the code it configures.

This is the mechanism that makes true isolation achievable. Section 13 treats it at length because the absence of it is the most common structural weakness in a Fabric CI/CD implementation.

3.5The repository model: mirrored folders#

The workspace folder structure is mirrored into the connected Git folder and vice versa. An item saved in Reports/Finance in the workspace is exported to Reports/Finance inside the connected folder. An item definition placed in a new folder in the repository produces a corresponding folder in the workspace on update. Folder depth is preserved to ten levels. Empty folders are not copied to Git, and empty folders in Git are removed automatically.

Figure 3 shows this mapping for a medallion example. The coupling is convenient and has one sharp edge, described in Section 7.4: because the folder structure is part of what is compared, a structural change made in the workspace puts the two sides out of step until it is committed.

3.6The branching model: GitHub Flow#

This playbook adopts GitHub Flow: main is always deployable, all work happens on short-lived branches created from main, and changes return to main only through a pull request. It is deliberately simpler than GitFlow, which maintains parallel main, develop, release and hotfix branches. For analytics work, where the goal is usually to iterate quickly on a bounded set of assets, the additional branch topology of GitFlow adds ceremony without adding safety — the protection comes from the review gate, not from the number of long-lived branches.

Section 11 sets out the model, the naming convention and the lifecycle in full, and Figure 6 traces a single change through it end to end.
