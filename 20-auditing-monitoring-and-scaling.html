20.3Scaling beyond one project#

The pattern described here is per project. Applying it to a dozen projects by repeating the configuration twelve times guarantees twelve variations. Four mechanisms prevent that:

  • Organization-level rulesets. Define the main protection once at organization level and apply it to every repository matching a naming pattern. New repositories inherit the protection rather than needing it applied. Organization-level rulesets are available on GitHub Team and Enterprise plans; enterprise-level rulesets are Enterprise-only.
  • Organization-level secrets, for the genuinely shared values only. Resist the temptation to centralize deployment credentials — see Section 17.1.
  • Reusable workflows. Define the deployment and verification workflows once in a shared repository and call them from each project, so a change to the deployment pattern is made in one place.
  • A repository template. A template repository carrying the CODEOWNERS file, the pull request template, the workflow definitions and the documentation stub means every new project starts correctly configured rather than being corrected later.
Practice

The template is the highest-leverage item

Most drift between projects originates in the first hour of a repository's life, when someone configures it from memory. A template removes that hour.

20.4Advanced testing#

Where the team is ready to go further than Section 18.4:

  • Unit-test notebook logic. Extract transformations into functions and test them with a standard framework. The constraint is usually notebook structure, not tooling — logic embedded in cells that assume a live lakehouse cannot be tested in isolation.
  • Data quality expectations. Assert properties of a transformation's output against a seeded dataset: row counts within bounds, no unexpected nulls in keys, referential integrity holding, totals reconciling.
  • Semantic model validation. Check that measures return expected values for known inputs. Surprisingly effective at catching the class of change that is syntactically fine and numerically wrong.
  • Make these required status checks on the main ruleset once they are stable — and not before.
