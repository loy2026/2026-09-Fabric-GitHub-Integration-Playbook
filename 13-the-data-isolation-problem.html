13The data isolation problem

This is the most important section in the playbook after Section 7. A branch workspace isolates code. It does not isolate data. Teams that do not address this get the appearance of isolation with none of the substance, and discover the difference when someone truncates a shared table.

Caution

Data is not copied to a branch workspace

Branch-out copies item definitions. A notebook in the new workspace that references a lakehouse will, by default, still connect to the lakehouse in the workspace it was branched from. The same is true of pipelines, dataflows and shortcuts.

13.1The two consequences#

13.2Option one: parameterization through a Variable Library#

This is the recommended approach and, since the Variable Library became available, the straightforward one. Design every item to be environment-aware: no hard-coded workspace names, lakehouse references, connection strings or database names. Each environment-specific value is a variable in a Variable Library, and each workspace has an active value set that supplies its own values.

Structure:

  • A Variable Library item lives in the workspace and holds named variables.
  • Variables may be basic types — string, integer, boolean — or complex types such as an item reference, which points at a specific lakehouse or warehouse.
  • Each variable has one value per value set. A value set corresponds to a stage (dev, test, prod) or to an individual developer's sandbox.
  • Exactly one value set is active in a workspace at a time, and it determines the values used at runtime.
  • Items resolve values from the active set in their own context — resolution is not tied to deployment.

Items that can consume a Variable Library include data pipelines, lakehouse shortcuts, notebooks (through NotebookUtils and the %%configure magic command), Dataflow Gen2, Copy Job, user data functions and Plan items.

The second benefit is centralization. If several lakehouses in a workspace use shortcuts to the same source, that source becomes one variable. Changing it is one edit rather than one edit per lakehouse.

13.3The design rule#

Rule

The design rule this all reduces to

No Fabric item may contain a hard-coded workspace name, lakehouse or warehouse reference, connection string or database name. Every environment-specific value belongs in a Variable Library and is selected by the active value set.

This one rule is what makes branch workspaces, deployment pipelines and deployment rules all behave as intended. Its absence is the most common reason a Fabric CI/CD implementation never stabilizes.

13.4Option two: automated data seeding#

Parameterization tells an item where to look. Seeding puts something there to find. A job triggered when a feature branch or branch workspace is created provisions a lightweight, isolated dataset for it.

  • Seed a small, representative, anonymized subset. The goal is a test that exercises the logic, not a copy of production.
  • Make it fast. A seeding process that takes an hour will be bypassed, and a bypassed control is worse than no control because it creates a false expectation.
  • Tear it down with the branch workspace, so cost tracks active development.
  • Treat anonymization as a requirement, not a nicety — a development workspace typically has a wider access list than production.
Note

Seeding complements parameterization; it does not replace it

A seeded dataset is only reachable if the items know to look at it, which requires the parameterization from Option 1. Implement the Variable Library first; add seeding when the team needs realistic data volumes.

13.5Choosing an approach#

Localize

This decision cannot be deferred

Record which approach you are adopting, which sources each value set points at, and who owns the seeding process if there is one. A branch workspace handed to a developer without this settled is a hazard presented as a sandbox.
