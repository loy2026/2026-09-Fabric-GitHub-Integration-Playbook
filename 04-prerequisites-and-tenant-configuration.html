4Prerequisites and tenant configuration

Nothing in this playbook works until a small number of gatekeeping settings are in place on both platforms. They are unremarkable individually; the reason they are treated carefully here is that they are usually owned by different teams, and the integration is frequently blocked by a setting nobody realised they needed to request.

4.1Capacity#

Git integration requires a Fabric capacity. All supported Fabric item types need one; an existing Power BI Premium capacity can be used, but certain Power BI SKUs support Power BI items only. Branch-out also requires available capacity at the moment the operation runs — a branch workspace must be assigned to a capacity to function, and a branch-out will fail if none is available.

Practice

Plan branch workspace capacity explicitly

A team of eight developers each holding an open branch workspace is eight additional workspaces drawing on capacity. Decide up front whether they share the main capacity or use a dedicated development capacity, and set an expectation that branch workspaces are deleted when their release ships.

Note

A permission change is coming

From 1 December 2026, users without read-write permission on workspace items cannot use Git integration. Where sensitivity labels or protection policies restrict a user's access to particular items, that user may lose the ability to use Git integration in that workspace. Audit which contributors hold partial item-level access before that date.

4.3GitHub prerequisites#

  • An active GitHub account for every person who will connect a workspace. The Git connection is per user — accounts and tokens are not shared.
  • A dedicated repository per project, created before the first connection and left empty of the folders Fabric will create. See Section 7.1 for why this matters.
  • Cloud-hosted GitHub, GitHub Enterprise Cloud or GitHub Enterprise Server. Several Enterprise Server configurations are unsupported: a custom domain (even when publicly reachable), hosting on a private network, and IP allow-listing.
  • Rulesets require a plan that includes them. Rulesets are available in public repositories on all plans, and in private repositories on GitHub Pro, Team and Enterprise Cloud. Push rulesets in private and internal repositories require Team or above, and some environment protection rules require Enterprise. Confirm the plan before designing the hardening in Sections 16 and 17 around them.
Note

If you are migrating from Azure DevOps

Fabric Git integration calls the underlying provider's APIs, and their capabilities and limits differ. Run validation tests before committing to a migration from Azure DevOps to GitHub Enterprise rather than assuming behavioural parity.

4.4Permissions required to perform each operation#

Two permission sets apply simultaneously: the role held in the Fabric workspace and the permission held in the Git repository. The more restrictive of the two governs. The tables below replace the permission screenshots in the source material and should be treated as the authoritative reference when troubleshooting an operation that is unexpectedly unavailable.

Rule

Commit to a protected branch will fail, and should

Once main carries a ruleset requiring pull requests, a workspace connected to main can no longer commit to it. This is the intended outcome. Development workspaces connected to main are update targets, not commit sources. All commits originate from branch workspaces on feature branches.

4.5Organizational coordination#

Three of the required capabilities — workspace creation, repository creation and workspace administration — are commonly held by a central platform or administration team rather than by the engineering team doing the work. This is a reasonable control, but it makes the integration a coordinated activity rather than a self-service one.

Localize

Agree the provisioning model before starting

Decide and record: who creates workspaces, who creates repositories, who holds workspace Admin, what the request path and turnaround expectation is, and whether the branch workspace admin profile described in Section 12.4 will be used to restore self-service branch-out without granting broad workspace-creation rights. A plan that assumes developers can create workspaces, in an organization where they cannot, stalls at the first branch-out.
