Part I · Foundations

1Executive summary

Fabric development without source control is a set of unversioned changes made directly to live workspaces by whoever has access. This playbook replaces that with a disciplined engineering practice: every change is versioned, reviewed by a second person, recoverable, and promoted through a controlled path. The mechanics are straightforward. The failure modes are not, and most of this document is about those.

1.1What the integration gives you#

Microsoft Fabric implements application lifecycle management through two complementary mechanisms. Git integration connects a workspace to a repository branch and folder, writing item definitions out as human-readable text so they can be versioned, branched, diffed, reviewed and restored. Deployment pipelines promote content across Development, Test and Production stages, rebinding environment-specific configuration as content moves. Git integration is the continuous-integration half; deployment pipelines are the continuous-delivery half. They are designed to be used together and neither replaces the other.

A third mechanism, the Variable Library, holds environment-specific values with a separate value set per stage. It is what allows the same item definition to point at different data in different workspaces. It did not exist in earlier iterations of this pattern and it is the single most useful addition, because it closes the gap described below.

1.2The ten conclusions that matter#

1.3What a successful implementation looks like#

At the end of the work described here, the following statements are all true of the environment, and each is independently verifiable:

  • No one can change production content without a peer-reviewed pull request — not because policy says so, but because the repository refuses the push.
  • Any change can be traced from the production artefact back to the commit, the pull request, the reviewer who approved it and the person who wrote it.
  • Any change can be reverted without reconstructing it by hand.
  • A developer can build and test in isolation without risk to shared data.
  • A person joining or leaving a team gains or loses access without a manual repository change.
  • Production deployment credentials are not readable by a workflow running on a feature branch.

Figure 1 shows how those statements fit together: three bands — isolated development, gated integration, controlled release — each of which is the subject of at least one section below.
