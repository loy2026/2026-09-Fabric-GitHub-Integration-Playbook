19Rollback and restore

The question that determines the method is not which command is cleaner. It is whether anyone else has pulled the commit. Get that wrong and a recovery becomes a second incident.

Figure 9 sets out the decision, both procedures, and the Fabric re-sync that must follow either of them.

19.1Choosing the method#

Rule

Never reset --hard a shared branch

Rewriting the history of a branch others have pulled leaves their local copies inconsistent with the remote. The next person to pull gets a confusing divergence, and someone will resolve it by force-pushing their own stale version back. If the commit has been shared, revert it.

The safe method, and the one to use for anything that has reached main. Scenario: a merged change has introduced a defect and must be undone without disrupting anyone else's history.

19.2.4Push#

The history on GitHub now contains a commit that explicitly undoes the problematic change, which is both a recovery and an audit record.

Caution

A protected main will refuse this push

If the ruleset from Section 16 is active, a direct push to main is rejected — correctly. Perform the revert on a branch and merge it through a pull request:

git checkout -b hotfix/<incident-id> → git revert <hash> → git push origin hotfix/<incident-id> → open a pull request.

Under a genuine production incident, an administrator with bypass may push directly. Record why.

19.3Method two: git reset --hard#

Caution

Destructive and history-rewriting

Use only on commits that have not been pushed to a shared branch, or after coordinating with everyone who has the branch. Work discarded by this command is not recoverable through normal means.

19.3.3Force-push#

Note

The feature branch ruleset will block this

Section 16.6 recommends Block force pushes on feature/**. That is a deliberate trade: it prevents accidental history loss on a branch a colleague may have pulled, at the cost of this recovery path. If you need it, the cleaner route is usually to abandon the branch and create a new one from the last good commit.

19.4Re-syncing the Fabric workspace#

Rolling back the repository changes nothing in Fabric. The workspace must be updated from the restored branch.

  1. Open the Fabric workspace connected to the branch you rolled back.
  2. Select the Source control icon.
  3. Open Updates. Fabric compares the workspace with the remote branch, detects that the branch has moved, and lists the items that must change.
  4. Review the list. Confirm it matches what you expect the rollback to affect — an unexpected entry means something else changed too.
  5. Select Update all, and confirm. Fabric overwrites the workspace items to match the restored commit.
  6. Verify the items run. Execute the affected pipelines, refresh the models, open the reports.
  7. Repeat for each workspace connected to that branch and folder.
Caution

Git restores definitions, not data

If the bad change wrote incorrect data — a mis-specified merge, a truncation, a bad backfill — then restoring the code does not restore the data. Data recovery is a separate exercise requiring a separate capability. Establish what that capability is before you need it.
