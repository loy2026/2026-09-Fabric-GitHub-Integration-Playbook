15Access model: teams, roles and identity

Least privilege is usually stated as a principle and implemented as an exception list. The way to make it hold is structural: grant permissions to a small number of teams whose membership comes from the identity provider, and never to individuals.

Figure 8 shows how identity, teams, repository roles and the gates they enforce relate to one another, and where the separate Fabric plane has to be kept aligned.

15.1Least privilege in this context#

Applied to a Fabric project, least privilege means moving away from the common state in which every developer holds administrative access to the repository. Access is tailored to the distinct functions in a data team:

  • Data engineers and developers need to write code and contribute changes on feature branches.
  • Lead developers and architects need to review and approve changes, and merge them into main.
  • Platform administrators and DevOps engineers need to configure repository settings, manage security and set up automation.
  • Auditors, compliance officers, project managers and business analysts need to see the code and track progress, and nothing more.

The reason to bother is not theoretical. The commonest cause of an unreviewed change reaching production is not malice — it is someone with admin rights merging their own pull request at the end of a long day because they could.

15.3Repository role reference#

To assign these, a repository administrator opens Settings → Collaborators and teams, invites each team, and selects its role. Grant roles to the teams, not to the people in them.

Rule

No individual collaborators

Every entry in Collaborators and teams should be a team. An individual added directly is invisible to the identity provider, survives the person changing role, and is found during an audit rather than during onboarding. If someone needs access, add them to a team.

15.4Centralized identity with Microsoft Entra ID#

Connecting the GitHub organization to Microsoft Entra ID moves access management from a repository task to a centrally governed function. The benefits are concrete:

  • A single source of truth. Identities and group memberships are managed in Entra ID, consistent with corporate identity policy.
  • Automated provisioning and deprovisioning (SCIM). Joining a team in Entra ID adds the person to the corresponding GitHub team. More importantly, leaving the organization or changing role revokes their repository access automatically. This closes the leaver gap, which is the most common real security finding in this area.
  • Simplified auditing. Access can be traced to the central identity provider rather than reconstructed from repository history.
Practice

Use the same groups on both planes

Grant the Fabric workspace roles to the same Entra ID groups that back the GitHub teams. A single group change then moves a person's access on both platforms at once. Maintaining two independent lists produces the 'it works for me' failures described below.

15.5Aligning Fabric workspace roles#

Repository roles grant no access in Fabric. The two planes are independent and must be kept aligned deliberately.

Note

The commonest misalignment

A developer has Write on the repository but only Viewer on the workspace, and reports that source control 'is not working'. They see nothing, because a Viewer sees no Git information. Check both planes before investigating anything else.

15.6CODEOWNERS#

A CODEOWNERS file maps paths in the repository to the teams that own them, and can be combined with a ruleset requiring review from code owners. In a layered structure this routes each change to the team that understands it.

Note

Any one code owner is sufficient

Where code has multiple owners, an approval from any of them satisfies the requirement. If you need approval from two specific teams, use the required reviewers capability in a ruleset (Section 16.4) rather than relying on CODEOWNERS.
