12Branch workspaces and isolated development

A branch workspace is the feature that makes this model practical in Fabric. It gives each unit of work its own live environment, which is the only way to test a change to a pipeline or a notebook without affecting anyone else. It also has one significant gap, which is the subject of the next section.

12.1What branch-out does#

Branch out is a single operation that performs several actions. From the source workspace's connected branch, Fabric:

  • Creates a new Git branch from the last commit of the source workspace's branch.
  • Creates a new workspace, or repoints an existing one, and connects it to that new branch.
  • Populates the workspace with the item definitions from the branch — all of them by default.
  • Establishes a recorded relationship between the branch workspace and its source workspace.

The developer is taken to the new workspace, which is then an isolated environment for that unit of work. The relationship is visible in the Fabric interface in three places: the workspace tree shows the source workspace as the parent; breadcrumbs allow navigation back to it; and the Related branches section of the Branches tab in the source control pane lists linked workspaces so they can be reached from the context of the current work rather than hunted for in a workspace list.

12.2The branch-out procedure#

  1. In the source workspace, open Source control and select Branch out.
  2. Choose whether to create a new workspace or branch out into an existing one. Enter the new branch and workspace names, or select the existing workspace.
  3. If a branch workspace admin profile is configured, decide whether to use it (Section 12.4).
  4. Optionally select Select items individually to include only a subset of items — see Section 12.3.
  5. Select Branch out. Fabric validates that your identity can complete the operation before starting, and reports an error rather than beginning an operation that would fail.
  6. Wait for the sync to complete; it may take a few minutes. Confirm you are in the new workspace and that the expected items are present.
  7. Establish data isolation before making changes — see Section 13.
Caution

Branching out to an existing workspace can lose work

Items in the target workspace that have not been saved to Git may be deleted. Commit anything you want to keep before branching out into an existing workspace. Fabric requires you to confirm you understand this before the operation starts — do not dismiss that confirmation reflexively.

12.3Selective branching#

By default a branch-out includes every item from the source branch. Select items individually limits the branch workspace to a chosen subset, which reduces the sync time and the capacity footprint — useful in a large workspace where a change touches three items out of two hundred.

  • All of a selected item's dependencies are required. The select related items control resolves them for you.
  • Selection can begin while Fabric is still calculating dependencies in the background, but proceeding before they have all loaded may cause the operation to fail. Wait.
  • A workspace created this way is identifiable by a selective branch indicator in the status bar.
  • Items can be added later: Source control → branch out symbol → Select additional items, choose from the items not previously selected, Add, then Update all.
  • Performing a switch branch in a selectively branched workspace resets the selection and synchronizes every item from the new branch.

12.4Branch workspace admin profiles: reconciling self-service with centralized control#

The tension described in Section 4.5 — branch-out needs workspace creation rights, and many organizations grant those only to a central team — has a direct answer in the platform. A branch workspace admin profile is configured by a workspace administrator on a Git-connected workspace. It presets a consented identity and a set of settings that Fabric then uses to create branch workspaces on that administrator's behalf.

When a developer branches out using the profile, Fabric performs the following as the administrator:

  • Creates the workspace.
  • Assigns it to a capacity.
  • Connects it to the Git repository.
  • Adds members to the new workspace with the role the profile specifies.

The developer needs no workspace-creation right of their own. The administration team keeps control of capacity assignment, membership and the security boundary, and the self-service branch-out experience is preserved. For most organizations this is the single most valuable capability in this section.

12.5Configuring a branch workspace admin profile#

  1. Open the workspace you want to enable, then Workspace settings.
  2. Select Git integration, then the Branch workspaces tab.
  3. Turn Allow branch workspace admin profile On.
  4. Under Role assignment, choose the role each developer receives on the branch workspaces they create.
  5. Under Admins, add the users or security groups to be made administrators of every branch workspace created with the profile. If the role assignment is Contributor or Member, at least one valid admin is required; Fabric blocks a branch-out that would create a workspace with no administrator.
  6. Under Capacity, choose Current active capacity to inherit the source workspace's capacity at branch-out time, or select another eligible capacity.
  7. Set Allow users with at least Contributor role to change Git branch — labelled Allow users with Contributor access or higher to change the Git branch on this tab. The value chosen becomes the default for every branch workspace created with the profile.
  8. Select Confirm. Fabric validates the configuration and creates the profile only if every check passes.

Validation confirms that you are a workspace admin; the workspace is connected to Git; you are signed in to your Git account and have access to the repository; you can create workspaces; you can assign the selected capacity and it is active; the capacity and the repository are in the same geographic region, or the tenant setting blocking cross-region operations is off (this check applies where the provider enforces it — see Section 4.2); and every identity in the Admins list is a valid tenant member.

Caution

The profile runs as a specific person

The workspace admin who last saved the profile becomes its consented identity. Every branch-out using the profile then runs under that person's identity. If a different admin edits and saves the profile, they become the consented identity instead.

A profile can also become invalid after it is created — a revoked permission, a deactivated capacity, or the consented admin leaving the tenant will all break it, and branch-out stops working until an administrator resolves the issue. Do not let the consented identity be a person who may leave. Assign it deliberately, review it as part of joiner-leaver process, and document who it is.

Note

Limitations

Branch workspace admin profiles were in preview at the time of writing, and a profile cannot be configured on a branch workspace — only on a source workspace.

12.6Switching branches and checking out a new branch#

Caution

Switch branch is the destructive one

Fabric requires you to confirm that you understand workspace items may be deleted and cannot be restored. The target branch must contain the same directory as the current branch. Switching does not affect the relationship between a branch workspace and its source workspace — it is a Git state change only.

12.7Branch-out limitations#

  • Requires available capacity at the moment the operation runs.
  • All workspace and branch naming limitations apply (Section 6.4).
  • Only Git-supported item types appear in the new workspace.
  • The Related branches list shows only branches and workspaces you have permission to view.
  • Branch-out creates a Git branch, yet its documented minimum Git permission is Read plus branch creation, whereas creating a branch from within Fabric by any other route requires Write. If a branch-out fails on permissions, grant Write and retest rather than assuming the documented minimum.
  • Settings from the original branch are not copied to the new branch. Adjust rulesets or definitions so the new branch still meets organizational policy — see Section 16.6.
  • Disconnecting a branch workspace from Git removes its relationship to the source workspace. Disconnecting a source workspace removes every branch workspace relationship it has.
  • Deleting a source workspace removes the relationships and leaves its branch workspaces as ordinary workspaces.
  • When branching out to an existing workspace: the target must support a Git connection, must have capacity, must not contain template apps, must not already have related branch workspaces, and you must be an admin of it (or a Contributor/Member with the branch-change setting enabled).
Practice

Automating branch-out

If you build an automation flow that reproduces what branch-out does, use the Create Workspace Relation API (preview) to establish the branch workspace relationship. Call it after the flow has created the workspace, created the Git branch and configured the connection — otherwise the workspace works but the relationship, and the navigation that depends on it, is missing.
