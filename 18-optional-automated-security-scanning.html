Part V · Security and governance

18Optional: automated security scanning

The manual gates in Sections 16 and 17 deliver most of the available risk reduction. This section is a worthwhile second phase, not a prerequisite — with one exception, noted below, which is worth enabling on day one.

18.1Secret scanning and push protection#

Of everything in this section, this is the one to enable immediately. A Fabric repository contains connection definitions, and the failure mode is a credential committed in a pipeline or notebook definition. Push protection rejects the push before the secret reaches the repository at all, which is qualitatively better than detecting it afterwards — a secret that has been pushed must be treated as compromised and rotated, even after the commit is removed.

  • Enable secret scanning and push protection in Settings → Advanced Security.
  • Add the Require secret scanning alerts are resolved rule to the feature branch ruleset so an unresolved alert blocks the merge.
  • Agree the response procedure in advance: rotate the credential first, then remove it from history. The order matters.
Note

Licensing

Secret scanning and push protection are free for public repositories. For private and internal repositories they require a purchased GitHub Secret Protection licence, which in turn requires a Team or Enterprise plan. If that is not available, the compensating control is a pattern-matching step in the CI checks of Section 18.4 — weaker, but not nothing.

Rule

A pushed secret is a compromised secret

Rewriting history does not undo exposure. Rotate the credential, then clean the repository. Never the other way round, and never only the second.

18.2Code scanning#

CodeQL analyses code for vulnerability patterns. Its value in a Fabric repository is narrower than in an application repository, because most of what is committed is JSON definitions rather than executable code. The useful target is the Python in notebooks and Spark job definitions.

  • Enable code scanning and configure CodeQL for Python.
  • Add Require code scanning results to the main ruleset, with a severity threshold you are prepared to enforce.
  • Expect to tune it. Notebook code triggers patterns that are not meaningful in a data engineering context, and an unusable alert list gets ignored wholesale.

18.3Dependency scanning#

Dependabot monitors declared dependencies for known vulnerabilities and opens pull requests to update them. In a Fabric repository the relevant surface is the library specifications in Environment items and any requirements files committed alongside notebooks.

Note

Environment items are where dependencies actually live

Fabric Environment items carry library specifications and are Git-supported. That makes them reviewable — a genuine gain, because environment drift is otherwise invisible — but the format may not be one Dependabot understands. Review environment changes manually in the pull request regardless of what automated tooling reports.

Practice

Start at stage 3

Stages 1 and 2 are hygiene. Stage 3 enforces the design rule that everything else in this playbook depends on, and can be implemented as a grep in a few lines of workflow. Do that one first.
