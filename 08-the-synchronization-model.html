8The synchronization model

Commit and Update look symmetrical and are not. Commit is selective and additive; Update is total and overwrites. Most day-to-day confusion about Fabric Git integration traces back to that asymmetry.

Figure 5 summarizes the model and the states a workspace reports between the two actions.

8.1Bidirectional, but never simultaneous#

Synchronization runs in one direction at a time. You cannot commit and update together. If changes have arrived in the branch, commits are disabled until the workspace has been updated. If the same item has been changed in both the workspace and the branch, updates are disabled until the conflict is resolved.

Rule

Update first, then commit

When both directions have pending work: update, resolve any conflict, verify the workspace still behaves, then commit. Attempting to force the sequence the other way produces conflicts that are harder to reason about than the ones you started with.

8.2Commit#

  • Changed items appear under Changes. Where more than one item has changed, you choose which to commit.
  • A commit message is optional; if omitted, a default is supplied. Supply one anyway — the default tells a reviewer nothing.
  • Commits are disabled while updates are pending.
  • During a commit, Fabric deletes files inside an item folder that are not part of that item's definition. Files elsewhere in the repository, outside item folders, are left alone. Do not store anything of your own inside an item folder.
  • A preview capability allows file-level commits within an item from the compare experience, for supported item types.

8.3Update#

  • Update always applies the entire branch and syncs to the most recent commit. Individual items cannot be selected — this is the principal asymmetry with commit.
  • Folder changes are applied along with item changes.
  • Items present in the workspace but absent from the branch are removed.
  • Updates are disabled if the same item has changed in both places, until the conflict is resolved.

8.6Diffs that are not really changes#

Several platform behaviours produce diffs that carry no functional meaning. Reviewers who do not expect them waste time on them, and — worse — start to distrust the diff.

  • Semantically insignificant reformatting. The service may rewrite definition files on commit. Renaming a semantic model column in Git and importing the change causes the Analysis Services engine to move that column to the end of the columns array in the .bim file on the next commit. Functionally irrelevant; visible as a change.
  • Line ending conversion. The service uses LF. An item edited locally and committed with CRLF — for example a .pbip saved from Power BI Desktop — will be converted to LF on the next commit from the service, producing a whole-file diff.
  • Enhanced Refresh API. Refreshing a semantic model through the Enhanced Refresh API produces a diff after each refresh.
  • Workspace identity. An item using a workspace identity, once committed, can only be updated back into a workspace connected to the same identity. This affects branch-out.
Practice

Say this out loud during onboarding

Tell new team members about line-ending and column-reordering diffs on day one. It takes thirty seconds and prevents a class of review comment that wastes an hour each time it recurs.

8.7Conflict resolution#

A conflict means the same item changed in both the workspace and the branch since the last sync. Fabric surfaces it; resolution is partly a Git operation. Two practical approaches:

  • Checkout new branch. Create a branch from the last synced commit, repointing the workspace at it without changing its content, then commit the workspace version to that branch and merge through a pull request. This preserves both versions and makes the reconciliation reviewable, which is usually what you want.
  • Discard one side. Either undo the workspace change and update from Git, or commit the workspace over the branch if the branch version is known to be wrong. Fast, and loses work — be certain which side you are discarding.

Conflicts are largely a symptom rather than a problem in their own right. They arise when two people work in the same workspace on the same branch. The branching model in Section 11 exists partly to make them rare.
