17Environments and credential management

Storing a production credential as a repository secret makes it readable by a workflow running on any branch, including a developer's experimental one. Environment secrets exist to prevent exactly that, and the difference is the single most consequential choice in this section.

17.1The three secret scopes#

Rule

Deployment credentials belong to an environment

A repository secret is readable by any workflow in the repository, on any branch. That includes a workflow a developer just wrote on a feature branch. Production credentials stored at repository scope are effectively available to anyone who can push a branch.

17.2Creating an environment#

  1. In the repository, go to Settings → Environments → New environment.
  2. Name it for the Fabric stage it corresponds to — development, test, production. Start with only the environments you actually deploy to; adding one later is trivial.
  3. Select Configure to set its protection rules.
  4. Add required reviewers (up to the platform limit) — the people who must approve a deployment to this environment. For production these should be a named, small group.
  5. Enable Prevent self-review so the person who triggered a deployment cannot approve it.
  6. Consider a wait timer for production, giving a short window in which an unintended deployment can be cancelled.
  7. Restrict deployment branches to main only for test and production. This is important: without it, a workflow on any branch can target the environment and read its secrets.
  8. Decide on Allow administrators to bypass configured protection rules. Enabling it provides a controlled break-glass path for incidents; it also weakens the control. If you enable it, expect every use to be accompanied by an incident record.
  9. Save the protection rules.
Note

Check your plan before designing around protection rules

On GitHub Free, Pro and Team, deployment protection rules such as required reviewers and wait timers are available for public repositories only. A private Fabric repository needs a GitHub Enterprise plan for those rules. Environment secrets still scope correctly without them, but the approval gate does not exist — so verify this before relying on a reviewer step in your design.

Caution

Restrict deployment branches, or the environment scope achieves nothing

Environment secrets are protected by the environment's rules. If any branch may deploy to that environment, then any branch can obtain its secrets and the distinction from a repository secret has been lost. Limiting deployment branches to main is what makes the scope meaningful.

17.3Storing the service principal credentials#

  1. Go to Settings → Environments and select the environment to configure.
  2. Scroll to Environment secrets and select Add secret.
  3. Create AZURE_TENANT_ID and paste the Directory (tenant) ID.
  4. Create AZURE_CLIENT_ID and paste the Application (client) ID.
  5. Create AZURE_CLIENT_SECRET and paste the client secret value.
  6. Confirm all three appear under the environment, and that none of them appears under Repository secrets.
  7. Repeat for each environment, using a different service principal per environment wherever possible.
Practice

One service principal per environment

Using one identity for development, test and production means a compromise anywhere is a compromise everywhere, and that the production identity is exercised by non-production jobs. Separate principals cost a little more administration and remove an entire class of blast radius.

Note

Secret values are write-only

Once saved, a secret's value cannot be read back through the interface — only replaced. GitHub also redacts secret values from workflow logs, though a workflow that deliberately transforms a secret can still leak it. Treat log output from any job with access to secrets as sensitive.

17.4Rotation without an outage#

Rotating a client secret naively causes a deployment failure at the worst possible moment. The sequence that avoids it:

  1. Create a second client secret on the existing Entra ID app registration, leaving the current one in place.
  2. Update the environment secret to the new value.
  3. Run a deployment, or a no-op workflow that authenticates, to confirm the new secret works.
  4. Delete the old secret from the app registration.
  5. Record the rotation date and set a reminder ahead of the next expiry.
Localize

Record the actual rotation interval and owner

An interval, a named owner and a calendar reminder. Without all three, rotation happens when a deployment fails.
