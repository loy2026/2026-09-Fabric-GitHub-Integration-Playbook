16Hardening the repository with rulesets

A protected branch is the difference between a policy and a control. Everything in Sections 11 to 15 describes how the team should work; this section is where the repository stops relying on them remembering.

16.1Rulesets rather than legacy branch protection#

Branch protection was historically configured through branch protection rules. Rulesets are the modern successor and are what this playbook uses. The differences are material:

16.2The main branch ruleset#

Create it from Settings → Rules → Rulesets → New ruleset → New branch ruleset. Give it a name that says what it does, for example main branch protection. Set Enforcement status to Active — a ruleset in evaluate mode reports but does not block.

Under Target branches, add a target by pattern and enter main, or use the Default branch inclusion so the ruleset follows the default branch if it is ever renamed.

16.3Recommended configuration for main#

Note

Why Restrict updates is deliberately absent from this list

Restrict updates is not the rule that forces changes through review — it is the rulesets equivalent of locking the branch. It permits pushes only from identities with bypass permission, and because merging a pull request is itself a reference update, enabling it on main blocks merges as well as direct pushes for everyone without bypass.

The rule that actually enforces the workflow is Require a pull request before merging, combined with Block force pushes and Restrict deletions. Reserve Restrict updates for a branch you intend to freeze entirely — for example a release/<version> branch after a regulatory filing.

Caution

Once main is protected, a workspace connected to main cannot commit to it

This is correct and intended. Development workspaces connected to main become update targets. All commits originate from branch workspaces on feature branches. If a team reports that they 'can no longer commit', the answer is that they should not be committing from that workspace — not that the ruleset should be relaxed.

16.4Required reviewers for specific paths#

Beyond CODEOWNERS, a ruleset can require review from specific teams when particular files or directories change. Up to 15 teams can be specified, each with its own required approval count, and each with a list of file patterns in .gitignore format. A team must hold write access or above for its approval to count, and a required approval count of zero adds a team for visibility without making it a gate.

Practice

Where this is worth the configuration

Gate the Variable Library and any shared OPS content behind an administrator approval. A change to an environment value affects every consuming item and looks trivial in a diff, which is exactly the combination that warrants an extra pair of eyes.

16.5Fabric-specific rules worth enabling#

Several ruleset rules map directly onto Fabric's own constraints. Enforcing them in the repository moves the failure from an obscure sync error to a clear push rejection with a message the developer can act on.

Note

Push rulesets have plan requirements

The file path, extension and size rules are push rules. In private and internal repositories they require the Team plan or above, and they apply to the repository and its entire fork network. Confirm your plan before relying on them.

16.6A feature branch ruleset#

Branch-out does not copy settings from the source branch to the new branch. If a feature branch needs to meet any standard, that standard has to come from a ruleset whose pattern matches it. A second, lighter ruleset targeting feature/**, bugfix/** and hotfix/** is therefore worth creating.

16.7Bypass permissions#

A ruleset can grant bypass to specific roles, teams or GitHub Apps. Some bypass capability is necessary — an incident at 02:00 with no reviewer awake is a real scenario — but it is the mechanism by which a control quietly stops being one.

Rule

Bypass is an audited exception, not a convenience

Grant bypass to a small, named group — fabric-admins — and never to fabric-developers. Expect a bypass to be accompanied by an incident record. Review bypass events in the audit log as a standing agenda item, not on suspicion.

For push rulesets, bypass permissions extend across the repository's entire fork network: only users who can bypass in the root repository can bypass anywhere in that network.
